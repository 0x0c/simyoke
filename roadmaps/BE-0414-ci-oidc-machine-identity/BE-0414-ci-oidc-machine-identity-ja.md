## はじめに

ホスティングされた`bajutsu serve`が今日認証する呼び出し元は、2種類です。人間はGitHub OAuth（Open
Authorization）でサインインし、身元を得ます。その身元をロールのゲートがエンドポイントごとに検査します
（[BE-0313](../BE-0313-github-org-team-rbac/BE-0313-github-org-team-rbac-ja.md)）。workerは共有トークン
（[BE-0051](../BE-0051-serve-hardening-for-hosting/BE-0051-serve-hardening-for-hosting-ja.md)）を提示し、
身元は一切持ちません。

継続的インテグレーション（CI）のジョブは、そのどちらでもありません。ブラウザでのサインインを完了でき
ず、OAuthを設定したデプロイでは、共有トークンがworkerのトラフィック以外のエンドポイントへ届かなくなり
ます。本項目は、そうしたジョブに固有の身元を与えます。ジョブはGitHub Actionsがワークフローに発行する
OpenID Connect（OIDC）トークンを、専用の交換エンドポイントへ一度だけ提示します。serveはそこでトークン
を検証し、代わりに短命の機械セッションを発行します。そして、そのセッションの振る舞うorgは、トークン
のクレームが名指すリポジトリで決まります。アクセス範囲は機械が必要とするものに絞り、人間の
ロールには決して寄せません。

## 動機

BE-0313は、serveのログイン許可リストをGitHub自身のorganizationとTeamのメンバーシップに置き換え、同じ
変更で共有トークンをworkerのトラフィックへ絞りました。人間にとっては、これは正しい判断でした。ロールの
ゲートが検査できる身元は、すべてを許す秘密より優れています。しかし機械には代替が残りませんでした。
`docs/self-hosting.md`はその結果をはっきり記録しています。トークンでworker以外のエンドポイントを
スクリプトしていたデプロイは、OAuthを有効にした時点でその経路を失います。

穴はリクエストのゲートに現れています。`bajutsu/serve/handler.py`の`_gate`はリクエストを認証したあと、
それが身元を運ぶかどうかで分岐します。OAuthのセッションは身元を持つため、`forbidden_for_role`が検査
します。bearerトークンのリクエストは身元を持たず、その先はコード自身のコメントが述べています。「stays
full-access (the operator credential)」です。つまりserveが知っている形は正確に2つで、CIのジョブは
どちらにも当てはまりません。

| 呼び出し元 | 資格情報 | 身元 | アクセス |
|---|---|---|---|
| 人間 | GitHub OAuthセッション | GitHubログイン | ロールで制限：viewer / editor / admin |
| worker | 共有トークン | なし | workerの経路で全権 |
| CIのジョブ | *（利用できるものがない）* | — | — |

共有トークンがまだ使えるデプロイでそれをCIに渡しても、この穴は閉じません。OAuthの場合を離れても理由が
2つあります。共有の秘密は、どのパイプラインの操作なのかを言えません。そのため監査の記録は「トークン」
までで止まります。そして身元を持たないため、全権で届きます。orgの設定を差し替えたり、シークレットを
埋め込んだconfigの本文を読み出したりできる資格情報が、すべてのパイプラインに置かれることになります。

具体的には、CIのパイプラインが呼ぶ理由のあるエンドポイント5つが閉じています。`POST
/api/artifacts/binary`と`GET /api/artifacts/exists`はadminロールを、`POST /api/run`はeditorロールを
要求します。本項目の兄弟にあたる、ジョブ単位のbinaryアーティファクト上書きの提案は、まさにこの順序
（ビルドをアップロードし、それを名指してrunをdispatchする）を求めています。しかしその提案が前提に
できるのは、トークン認証のデプロイがすでに信頼している資格情報だけです。OAuthのデプロイでは、前提に
できるものがありません。ビルドとあわせて設定やシナリオ一式を公開するパイプラインもあります。そうした
パイプラインには、さらに2つのadmin向けルート、`POST /api/artifacts/config`と
`POST /api/artifacts/scenarios`が必要です。そのため、以下の許可リストはbinaryだけでなく、アーティ
ファクトの3種類すべてを対象にします。このパイプラインは、公開したものを人間が後からcomposeするための
運び手ではなく、公開したものの利用者そのものです。アップロードしたばかりの3つ組に対して、シナリオを
名指して実行します。その3つ組が、`POST /api/compose`が行うorg全体の差し替えなしにどう有効になるかは、
単位3で述べます。

**検証可能な成果。** `permissions: id-token: write`を宣言し、**リポジトリのシークレットを一切持たない**
GitHub Actionsのワークフローが、OAuthを設定したデプロイに対してrunをdispatchします。そのrunは、
ワークフローのリポジトリが属するorgに着地します。orgが列挙していないリポジトリのワークフローは403で
拒否されます。そして、runの監査記録にはそのリポジトリ名が残ります。トークンが提示されたという事実だけ
ではありません。

## 詳細設計

作業はMECE（漏れなく重複なく）に4つの単位へ分かれます。トークンの検証、クレームからorgへの対応づけ、
機械に何を許すかの決定、そしてテストとドキュメントです。

### 単位1 — トークンを一度だけ機械セッションに交換する

本項目が対象とするパイプラインは、`GET /api/artifacts/exists`、`POST /api/artifacts/binary`、
`POST /api/run`の順に3つを呼びます。OIDCトークンをリクエストのたびに検証し、
一度見た`jti`は拒否する仕組みだと、2回目の呼び出しでこの並びを拒否してしまいます。1回目の呼び出しで
すでに`jti`を使い切っているからです。使い捨ての再送防止をリクエストのたびに課す仕組みでは、この
パイプラインを扱えません。そこでserveは、専用の交換エンドポイント`POST /api/oidc/exchange`でトークン
を一度だけ検証し、代わりに短命の**機械セッション**を発行します。この並びの後続の呼び出しは、すべて
このセッションを提示します。以下の各検査は内容をそのまま残しつつ、リクエストのたびにではなく交換の
一度だけになります。

GitHub Actionsは、`permissions: id-token: write`を宣言したワークフローのジョブに対して、署名済みの
JSON Web Token（JWT）を発行します。ジョブは`$ACTIONS_ID_TOKEN_REQUEST_URL`へ
`$ACTIONS_ID_TOKEN_REQUEST_TOKEN`を添えて要求します。どちらも、その権限を宣言したジョブから使えます。
GitHub側にGitHub App、OAuth app、Identity Providerの登録は一切必要ありません。ジョブはその結果を
bearerトークンとして交換エンドポイントへ送ります。serveはそこで署名を検証してから、クレームを信頼
します。

- **発行者。** `iss`は設定された発行者と一致しなければなりません。GitHubがホストするActionsであれば
  `https://token.actions.githubusercontent.com`です。
- **署名。** 発行者のJSON Web Key Set（JWKS）に対するRS256です。JWKSは
  `/.well-known/openid-configuration`から辿り、有効期限つきでキャッシュします。交換のたびに鍵を
  取得しにいくことはしません。検証器は、許可するアルゴリズムとしてRS256だけを渡します。ヘッダーが別の
  アルゴリズムを名指すトークンは拒否します。アルゴリズムをトークン自身に選ばせることはありません。
  `alg: none`や、HS256をRSAの公開鍵バイト列で検証させる、あの典型的なJWT攻撃を防ぐためです。発行者の
  discoveryドキュメントはRS256だけを広告しているため、この制約に費用はかかりません。JWKSの各項目は、
  鍵の種類がRSAであり、広告されたアルゴリズムも一致する場合にだけ使います。キャッシュにない鍵ID
  （`kid`）は更新を発生させますが、最小の更新間隔を設けます（または、直近に見つからなかった鍵IDを
  一定時間ネガティブキャッシュします）。そうしないと、交換エンドポイントへ到達できる人は誰でも、認証
  される前にランダムな`kid`を使ったリクエストで外部への鍵取得を1回ずつ強制できます。これは、この
  キャッシュ自体が防ごうとしている増幅そのものです。この増幅が及ぶ範囲は、今ではあらゆるリクエスト
  ではなく交換エンドポイント1つに絞られています。それでも上限はなお重要です。このエンドポイントは
  事前の資格情報を必要とせず、誰でも到達できるからです（単位3）。この鍵取得には、明示的なタイム
  アウトを設けます。ゲートはstdlibバックエンドで同期的に動くためです。鍵セットを取得できず、キャッシュ
  も失効している場合は、古い鍵セットではなく交換を拒否します。ローテーションで外れた鍵を、有効なまま
  にしておくわけにはいきません。それでも検証できない署名は、閉じる方向で失敗します。
- **想定利用者。** `aud`は**デプロイ側**が設定した値と一致しなければなりません。これは、オペレーターが
  省略してはならない唯一の検査です。想定利用者はワークフローが自分で選べます（`core.getIDToken(audience)`
  が引数に取ります）。そのため、任意の`aud`を受け入れるデプロイは、無関係なサービス向けに発行された
  トークンを受け入れることになります。デプロイがどの想定利用者も設定していない場合は、OIDCの呼び出し
  形態そのものを無効にします。OIDCトークンを提示する交換のリクエストは、無条件に拒否します。任意の
  `aud`を受け入れる側へ倒れることはありません。これは、運用者の注意力ではなく、閉じる方向の失敗に頼る
  設計です。
- **有効期間。** `exp`・`nbf`・`iat`を、わずかなずれの許容とともに検査します。この許容は、
  `bajutsu/common/github/app.py`がApp JWTに署名するときすでに適用している60秒の遡りと同じ考え方です。
  `iat`を持たないトークンは、そのまま拒否します。下記のserve側の経過時間上限が、`iat`がなければ
  測る起点を持てないためです。`jti`の欠落に適用しているのと同じ、閉じる方向の失敗規則です。
- **再送・使い捨て・レプリカ間の共有。** GitHubは数値の有効期間を文書化していません。トークンはbearer
  の資格情報であり、捕捉した者は有効な間ずっと再送できます。これは、代替案で述べた「ログに漏れる秘密が
  ない」という利点と相性が悪い事実です。serveは、トークンの`jti`クレームをキーにした再送検知キャッ
  シュを保持します（GitHubは`jti`を一意な識別子として文書化しています）。このキャッシュは、トークン
  自身の`exp`で有効期限を区切り、さらに`exp`とは独立に、serve側で定めた最大経過時間を超えたトークン
  も拒否します。`jti`を持たないトークンは、そのまま拒否します。単位2が`environment`クレームの欠落に
  適用しているのと同じ、閉じる方向の失敗規則です。このキャッシュは、共有のsystem of record、
  `Repository`という接続点に置きます。暗号化された組織ごとのシークレット保管が書き込む先と同じデータ
  ベースであり、こちらは自らの`SecretStore`という接続点を経由します。`docs/self-hosting.md`は、ホス
  ティングされた制御プレーンを、そのストアを共有する複数のレプリカとして記録しています。プロセスごとの
  キャッシュだと、捕捉したトークンを別のレプリカへ再送すればすり抜けられてしまい、実際の歯止めは経過
  時間の上限だけになります。費用はジョブ1件につき書き込み1回です。交換はリクエストのたびにではなく、
  ジョブ1件につき一度だけ起きるからです。一度使われた`jti`が再び提示されると、最初に使い切ったレプリカ
  でも別のレプリカでも拒否します。

検証には[`joserfc`](https://jose.authlib.org/)を使います。joserfcは、JWS・JWT・JWK鍵セットを一通り
扱う、保守が続いているJOSE（JavaScript Object Signing and Encryption）実装です。joserfcは、`oauth`
extraの依存として保証されているわけではありません。authlibの依存になったのは`authlib` 1.7.0からです。
`oauth = ["authlib>=1.3", "httpx>=0.27"]`は、それより前のリリースを下限として宣言しています。今日
インストールされているのは、`uv.lock`がたまたま`authlib` 1.7.2を固定しているからにすぎません。そこで単位1は、authlibの推移的な依存に頼るのではなく、`joserfc`を
`oauth` extraへ直接宣言します。extraは、コードが実際にimportするものをそのまま言うようになり、
`joserfc`を残すためだけにauthlibのアップグレードを強いることもなくなります。このライブラリは、
現行のlockではすでにインストールされています。この変更が保つのは、authlib自身の依存関係が今後
どちらへ動いても、その状態が変わらないという事実です。BE-0224は別のconfigソースの関心事としてApp
JWTに`cryptography`で署名していますが、本項目はその仕組みに触れません。

交換エンドポイント自身の検証（JWKSの取得とそのキャッシュ、そして上記の各検査）は、専用のモジュールに
置き、OIDCを設定したときにだけ遅延importします。`bajutsu/serve/gate.py`が持つのは、機械セッション
のポリシー判断（単位3）だけです。`bajutsu/serve/__init__.py`は`gate`を無条件にimportします。`joserfc`は`oauth`
extraにしか付属しません。そのため`gate.py`内でモジュールレベルの`joserfc`をimportすると、ベース
インストールとworker extraのすべてで`import bajutsu.serve`が例外を送出します。単位4は、
`tests/serve/test_import_guard.py`の`FORBIDDEN`集合へ`joserfc`を追加します。この集合は今日`authlib`
を挙げていますが`joserfc`は挙げていません。この抜けを放置すると、この回帰には誰も気づけません。

**セッションストアは、この設計に必要なものを備え、保証できないものは交換そのものを拒否します。**
`SessionStore.issue()`は今日、有効期限の引数を取りません。有効期間はストア単位です
（`BAJUTSU_SESSION_TTL`、デフォルトで7日間）。トークン自身の`exp`は、ストア単位の有効期間では表現できません。
そこで単位1は、Protocolと3つの実装すべてへ、機械セッションごとの有効期限を追加します。対象は
`in_memory_session_store.py`、`server/sessions/sql_session_store.py`、
`server/sessions/redis_session_store.py`です。あわせて、`id`・`identity`・`expires_at`に加えて2つの列をセッ
ションの記録へ加えます。解決済みの**org**と**principal kind**であり、単位3がこれをリクエストごとに
読みます。`InMemorySessionStore`は有効期限を一切保証しません（`return sid in self._sessions`）。
そのため、**セッションごとの有効期限を保証できないストアでは、交換そのものを拒否します**。想定利用者
が未設定の場合と同じ、閉じる方向の失敗であり、OIDCの呼び出し形態を、OAuthを設定しデータベースを配線
したデプロイに絞ります。発行する機械セッションの有効期間も、トークン自身の`exp`を上限とします。この
交換がトークンをそのまま再利用するより優れているのは、発行する資格情報がトークンより短命な場合だけ
です。

上記の`sessions`の2つの列と`jti`の再送検知テーブルは、どちらもスキーマの変更であり、これまでの追加と
同じように、`bajutsu/serve/server/migrations/versions/`配下のAlembicのrevisionを伴います。後者は
キャッシュのように読めますが、他と変わらないテーブルです。revisionがないと、既存のデプロイを更新した
ときに、`sessions`テーブルにない列を選択し、存在しないテーブルへ行を書くコードが動いてしまいます。
この設計が対象を絞っている、まさにデータベースを配線したデプロイで、交換が実行時に失敗します。

**この交換が買うもの、買わないもの。** どちらもTLS越しのbearer資格情報であり、捕捉された資格情報への
耐性はほぼ変わりません。正直な違いは有効期間だけであり、だからこそ上記の上限が重要です。変わるのは
次の4点です。機械セッションは**取り消せます**（単位3が与える身元によってです。GitHubが発行した
トークンは、serveが取り消せません）。JWTの検証とJWKSの取得は、リクエストごとの経路から完全に外れ、
そのコードが認証前に到達できるのは交換の1回だけになります。使い捨ての`jti`がそもそも可能になり、盗ま
れたトークンは静かな成功から**目に見える失敗**へ変わります。攻撃者側の交換が`jti`を使い切るため、
正規のジョブ側の交換は大きな音を立てて失敗します。発行されたセッションは、他のどのサービスにも
無価値です。`aud`を他のサービスも受け入れてしまう可能性があるトークンとは違います。費用は、エンド
ポイントが1つ増えること、セッションの有効期間を正しく決めること、ジョブの間だけパイプラインに第二の
資格情報が増えることです。交換のあと、機械のリクエストはJWTを一切運びません。あらゆる人間の
リクエストがすでに通っている経路と同じセッションの照合を通ります。照合先のセッションは、OAuthの
コールバックが人間のセッションを発行するのとまったく同じ`state.auth.issue_session()`で発行された
ものです。OAuthが無効にするのは`authz.login()`、つまりトークンによるサインインのほうであり、機械
に対してはこの交換がその代わりを担います。

### 単位2 — クレームそのものでorgへ対応づける

`OrgConfig`（`bajutsu/serve/orgs.py`）は、orgに誰が属するかをすでに宣言しています。`members`、
`githubOrgs`、`githubTeams`、`editorTeams`、そしてそのorgが所有する`targets`です。本項目はここへ
`allowedRepositories`を追加します。各項目は`"<owner>/<repo>"`という文字列です（この項目をさらに
絞り込むオブジェクトにもできます。後述します）。**交換のリクエストは、
使いたいorgを必ず名指します。** そのorgの`allowedRepositories`がトークンのリポジトリを列挙していれば
交換は成功し、列挙していなければ拒否します。規則はこれだけです。

orgの名指しは**選ぶだけで、権限を与えません**。リクエストが言うのは、どのorgに対してクレームを照合
するかだけです。通すかどうかは照合の結果が決めます。`worker_lease`の規律（orgは検証済みの出所から
取り、呼び出し元の申告からは取らない）を、一段上へ適用した形です。

名指しを求めることが、1つのリポジトリを複数のorgで使えるようにします。これは実在する形で、異なる
チームのアプリを検証する共有のパイプライン用リポジトリが該当します。推測に頼ると、この形を禁じるか、
列挙している複数のorgから勝者を選ぶかになります。人間はこの曖昧さを事後に解消できます。`eligible_orgs`
に裏打ちされたヘッダーのorgセレクターがあり、どこに着地したか見えて切り替えられるからです。パイプ
ラインには何も見えないため、同じ事後の選択では複数のテナントのどれかへ静かに着地します。ワークフロー
でorgを名指せば、狙う先はすでに書き記されている場所で明示され、判定は1回の所属確認に縮みます。機械
セッションがそれを記録するので、交換時に決まり、リクエストごとに導出し直すことはありません。

**`allowedRepositories`が`"<owner>/<repo>"`という名前を使い続けるのは、意識して受け入れた
トレードオフです。** 軽い注意書きではありません。`repository`は*可変の*名前です。名前の再利用こそ、
GitHubがimmutableなsubjectを導入した理由そのものです。列挙したリポジトリが削除、リネーム、または
譲渡されると、その名前は空きます。次にその名前を得た人は、列挙した項目と一致する`repository`クレーム
を持つトークンを発行できてしまいます。本項目は名前による形を維持します。そのため、運用者には責務が
生まれます。リポジトリがリネーム、譲渡、または削除された瞬間に、項目を削除または更新しなければなり
ません。項目が認めているのは名前であって、リポジトリそのものではないからです。

**設定が効力を持つのは交換のときだけです。** リクエストごとに検証する設計であれば、項目の削除や
`environment`/`ref`による絞り込みの強化は、次の呼び出しから効力を持ちました。一度きりの交換では、
すでに発行された機械セッションが、古い絞り込みのまま、有効期限が切れるまでそのorgとして振る舞い
続けます。これが、上で述べた名前再利用という露出の実際の被害範囲です。運用者の責務は、項目を削除ま
たは更新するだけでなく、その項目のために発行された機械セッションを取り消すことにも及びます。単位3
が与える身元（`repo:<owner>/<repo>`）を使います。

**`sub`を解析するのではなく、個別のクレームで一致させます。** トークンは`repository`と
`repository_owner`、さらに`repository_id`と`repository_owner_id`を運びます。認可は`repository`を
完全一致で比較します。`sub`を読むのが誤りである理由は2つあります。

- **`sub`の形式は、新しいリポジトリについてはすでに変わりました。** 2026年7月15日より後に作られた
  リポジトリは、数値のIDを埋め込んだimmutableなsubjectを得ます。
  `repo:octo-org@123456/octo-repo@456789:ref:refs/heads/main`という形です。GitHubは、その日付より後
  のリネームや譲渡も、immutableな形式へ移します。そのため、列挙済みのリポジトリが、誰も選んだ覚えの
  ないまま形式を変えることがあります。これは、上で述べた名前再利用への注意を、いっそう必要にする事実
  です。それ以前のリポジトリは、明示的に切り替えないかぎり以前の形のままです。immutableなsubjectは、
  GitHub Enterprise Serverでは使えません。`sub`を解析するデプロイは、あらゆる形式を扱わねばならず、
  どれかを黙って読み違えます。
- **`sub`はカスタマイズできます。** リポジトリは、`include_claim_keys`という配列でsubjectを構成する
  クレームを再定義できます。organizationが提供できるのはテンプレートだけです。すでにOIDCを使っている
  リポジトリがオプトインしないかぎり、organizationのテンプレートはそのリポジトリに影響しません。権限
  はorganizationではなくリポジトリの側にあります。したがって`sub`の内容は、serveが前提にしてよいもの
  ではありません。

完全一致は前方一致も排除します。ここでの典型的な失敗が前方一致です。`repo:acme/app`は
`repo:acme/app-evil`にも前方一致するため、部分一致の判定はオペレーターが列挙していないリポジトリを
通してしまいます。

**リポジトリは信頼境界のすべてではありません。** 列挙されたリポジトリにワークフローの変更をマージできる
人は誰でも、そこからトークンを発行させられます。つまり`allowedRepositories`だけでは「そのリポジトリの
ワークフローを書ける人は、このorgとしてdispatchできる」という意味になります。より厳しい境界が必要な
デプロイは、トークンがすでに運んでいるクレームでさらに絞ります。`environment`（GitHubのEnvironmentは
ジョブの実行前にレビュアーを要求できます）、`ref`、`job_workflow_ref`です。これらは**項目ごとに**
設定します。org全体にはかけません。`allowedRepositories`の各項目は、素の`"<owner>/<repo>"`という
文字列か、その名前に加えて独自の`environment`/`ref`/`job_workflow_ref`の境界を運ぶオブジェクトの、
どちらかです。そのため、あるorgがGitHubのEnvironment配下で動くリポジトリと、そうでないリポジトリを
並べて列挙でき、境界のない項目を置くためだけに別のorgを用意する必要がありません。`environment`は
*条件つきの*クレームです。GitHubは、ジョブがenvironmentを参照するときにだけ、このクレームを発行しま
す。そのため、`environment`の境界を設定すると、クレームの値が異なるトークンだけでなく、クレームを
欠くトークンも拒否します。そうしないと、environmentを宣言しないジョブが、この絞り込みをまるごとすり
抜けてしまいます。

1つの危険は、コードではなくドキュメントに属します。forkからのpull requestは、既定では
`id-token: write`を受け取りません。しかし`pull_request_target`のワークフローはbaseリポジトリの文脈で
動くため、受け取れます。同じ危険は、fork由来のpull requestへ書き込み用のトークンを送るリポジトリ設定
にもあります。この設定は、素のfork pull requestでも`id-token: write`を再び有効にします。
`pull_request_target`を使うパイプライン、またはこの設定を有効にしたパイプラインを持つリポジトリを
列挙するデプロイは、environmentで絞るべきです。外部の貢献者が影響を与えた実行から、トークンを発行
させないためです。

### 単位3 — 人間のロールではなく、機械の主体として扱う

交換が発行する機械セッションは、OAuthのセッションと共有トークンに並ぶ**3つ目の呼び出し元の形**
です。セッションと同じく身元を運び、しかも人ではないため、viewer / editor / adminというどの序列でも
表せません。何を許すかは、エンドポイントの明示的な許可リストで決めます。

| 許可 | 拒否 |
|---|---|
| `POST /api/artifacts/{config,scenarios,binary}` | `POST /api/config`、`POST /api/compose`（orgのアクティブな設定の差し替え。パイプラインが代わりに使うものは後述） |
| `GET /api/artifacts/exists` | `GET /api/config/content`（configの本文はシークレットを埋め込み得ます） |
| `POST /api/run`と、自分のorgのrunの読み取り | `POST /api/apikey`、`POST /api/claudecodetoken`（オペレーターのシークレット） |
| | `/api/orgs*`（誰がサインインし書き込めるか） |

**アーティファクトの公開は、パイプラインに必要なことの半分であり、その残り半分は`POST /api/compose`
ではありません。** 実際のパイプラインは、ビルドと一緒にconfigとシナリオツリーをアップロードし、その
3つに対してシナリオを名指して実行します。そのため、上記の3つのアップロード経路だけでは、有効化する
手段のないバイトを抱えたままになります。`bind_artifact`はそれ単体では何もバインドしません。とはいえ、
`POST /api/compose`でその穴を塞ぐのは誤りです。この経路はorgの**アクティブな**設定をバインドし、さらに
`remember_org_config_source`を通じてorgの記憶された設定も書き込みます。そのため、メンバーの次の
セッションは、最後にパイプラインがcomposeしたものを引き継いでしまいます。加えて、同じリポジトリの
同時実行ジョブは、それぞれが求めたものを実行するのではなく、1つのバインディングを取り合うことに
なります。どちらも、姉妹提案であるジョブ単位のbinary上書きが、dispatchのたびに差し替えを求めることを
拒否した理由そのものであり、binaryに当てはまるのと同じように、3つ組にも当てはまります。

したがって、パイプラインの3つ組は、その姉妹提案がbinaryを有効化するのと同じ方法で有効化します。
**dispatch時に名指す、ジョブ単位のアーティファクト参照**であり、runのためにマテリアライズされ、何も
バインドしません。`materialize_composition`は、`state.bind_upload`や`remember_org_config_source`とは
独立に、3つ組をcontent-addressedなツリーへ組み立てます。そのため、ジョブ単位の3つ組に、新しい
composeの仕組みもバインディングのスロットも要りません。これは、機械セッションが上記のセッションなしの
`binding_for`の経路を保てる理由でもあります。本項目はそのフィールドを規定しません。姉妹提案が
`binaryArtifact`の上書きを、binaryのレッグから3つ組へ広げることに依存します。この拡張こそ、姉妹提案の
「検討した代替案」が却下しているものであり、その根拠は、CIがbinaryだけを変えてconfigとシナリオは固定
するという前提です。本項目の動機となるケースは、その前提を満たしません。

`POST /api/oidc/exchange`自体は、この許可リストの外にあります。入口そのものであるため、事前のserve
の資格情報を必要とせず、検証可能なOIDCトークンだけを求めます。上の表を入口のゲートだと読んではいけ
ません。この表が決めるのは、すでに発行された機械セッションできることであり、トークンがセッション
になる経路ではありません。そこへ実際に到達するには、別の変更が要ります。`gate.is_open`のPOSTの分岐
（`bajutsu/serve/gate.py`）は今日、`path == _LOGIN_PATH`そのものです。そのため、認証前のリクエストは
他のどの経路でも、検証が走る前に401で拒否されます。単位3は`POST /api/oidc/exchange`をその分岐へ加え
ます。OIDCを設定したときにだけ有効にし、想定利用者を設定していないデプロイでは経路を閉じたままにしま
す。上と同じ、閉じる方向の失敗規則です。

**機械セッションが運ぶ身元。** 機械セッションは、取り消し可能であるために、`None`ではない身元を
必ず運びます。`revoke_identities`は身元の文字列で取り消しを行い、そのdocstringは、身元を運ばない
セッションには一切触れないと述べています。GitHubのログイン名と衝突しない予約形式を与えます。ログイン
名は`/`を含めないため、`repo:<owner>/<repo>`とします（`users.id`ではありません。下の監査エントリを
参照してください）。`revoke_identities`の今日の唯一の呼び出し元はorgの廃止です。単位3は、運用者が
orgそのものを廃止せずに、あるリポジトリの発行済み機械セッションだけを取り消せるよう、取り消しの経路を
公開する責務を負います。取り消しの粒度はジョブ単位ではなくリポジトリ単位です。あるリポジトリが発行
するセッションはすべて同じ身元を共有するため、取り消しはそのリポジトリの実行中のパイプラインも
まとめて終了させます。この共有される身元こそが、単位2の運用者の責務が前提としているものです。
同じ理由で、orgの廃止そのものにも手を入れる必要があります。`delete_org`が取り消すのは
`list_org_user_ids`が返す名簿であり、これは`users`テーブルを読みます。機械にはそこに行がありません。
そのため、orgを廃止するときは、そのorgに紐づく機械セッションも取り消さなければなりません。さもないと、
機械セッションは有効期限が切れるまで、廃止されたテナントとして振る舞い続けます。BE-0375がこの取り消し
を追加して塞いだ、まさにその漏れです。

runの読み取りは**org**単位であり、行為者ごとではありません。読み取りの経路は`org_id`を引数に取り、
`created_by`では絞り込みません。`created_by`は`runs`にすでに存在する、`users.id`へのnullを許す
foreign keyです（`bajutsu/serve/server/models/run.py`）。機械は、自分が始めたrunだけでなく、所属org
全体のrunを読み取ります。`bajutsu/serve/jobs.py`は、行為者が実在するuserであるときにだけ`created_by`
を書き込みます。トークンやCIのrunには行為者がいないと、そのコード自身のコメントが述べています。その
ため、機械がdispatchしたrunはこの列をnullのままにして済みます。合成の`users`行がなければ満たせな
かったはずの、2つ目のforeign keyです。それを超える、run単位の帰属づけはまた別の変更になります。

この許可リストが、パイプラインへ渡して安全だと言える根拠です。開くエンドポイントのうち4つは今日adminで
あり、機械にadminという**序列**を与えると、設定の差し替えとシークレットの読み出しが付いてきます。
エンドポイントを名指す方式なら、機械の手が届く範囲はアーティファクトの公開とrunの開始にとどまります。
これはパイプラインが必要とするものの全体です。`required_role`は人間が必要とするものを決め続けます。
この許可リストは機械の主体に対してのみ参照され、他では参照されません。そのため、どちらのゲートも他方を
広げることはありません。

この許可リストは、機械の主体に対して無条件に適用します。データベースの配線とは関係ありません。
`forbidden_for_role`は`state.repository`が`None`のとき許可を返します（`bajutsu/serve/authz.py`の
「DB-less = full access」）。同じ接続点に許可リストを置いても、データベースの有無で条件分けすれば、
この開いた振る舞いをそのまま受け継いでしまいます。そもそも、データベースを持たないデプロイに
機械セッションは存在し得ません。単位1の交換が拒否するからです。そのためこれは生きた経路ではなく、
二重の安全策です。

両方のバックエンドが守る共有の方針は、`handler.py`の`_gate`だけではなく、`bajutsu/serve/gate.py`
（BE-0253）にあります。stdlibのhandlerとFastAPIのアプリが、セキュリティ上の姿勢で食い違わないように
するための場所です。このモジュール自身のdocstringは、以前の重複を「セキュリティ上の食い違いへ静かに
至る道筋であり、それを検知する仕組みは何もない」と呼んでいます。`bajutsu/serve/server/app.py`は
`handler.py`を1行ずつなぞっています。単位3の機械セッションの許可リストは、`gate.py`がすでに守って
いる人間のロールゲートと並んでそこに実装します。そのため、両方のバックエンドが同じ場所から機械の
主体を得られます。単位1のトークン
検証は、専用の遅延importモジュール（前述）に置き、交換エンドポイントだけがそこへ到達し、`gate.py`
自身は到達しません。機械セッションは、人間のセッションとまったく同じ形で認証されます。有効な
セッションCookieであり、`gate.is_authorized`はすでに、そのどれに対しても真を返します。新しい分岐は
`forbidden_for_role`の隣に置き、セッションの記録が運ぶprincipal kind（単位1）で分けます。
`forbidden_for_role`は機械の主体に対して走らせてはいけません。身元不明のユーザーはデフォルトで
viewerとなり、viewerは`POST /api/run`を拒否するからです。代わりにエンドポイントの許可リストが決め
ます。人間のセッションが決してそこへ到達しないようにしているのも、このprincipal kindです。

**orgは機械セッションとともに運ばれ、`org_of`は経由しません。** 今日、`start_*`で始まる各エンド
ポイントは`state.org_of(actor)`を通じてorgを決めます。これは行為者について永続化されたuserの行を
読みます。許可リストが開くエンドポイントも同じです。`bind_artifact`と`artifact_exists`
（`bajutsu/serve/operations/upload.py`）、そして`bajutsu/serve/operations/reads.py`のrun読み取りの
経路です。どれも`org = state.org_of(actor)`を取り、object-storeのキー・ローカルキャッシュの
パス・監査の行・存在確認のprobeに使います。機械にはその行がないため、`org_of`は`allowedRepositories`
にかかわらず、これらすべての呼び出しで`default`を答えてしまいます。マルチorgのデプロイでは、まさに
許可リストが最初に開くこれらの経路が、テナントをまたぐ穴になります。そもそも
`Repository.get_run(run_id)`はorg単位ではなく、`session.get(Run, run_id)`に`org_id`はなく、これを
土台にしたrun単位の読み取りは、それ自体のテナント境界を持ちません。代わりに、許可リストにある
すべての操作は、交換（単位1）で一度解決したorgを機械セッションから読みます。機械セッションはまた、
セッションごとのスロットを取らず、セッションを渡さずに`binding_for`を呼んで設定を解決します。これは、
CIからのリクエストについて`binding_for`がすでに文書化している、デプロイのフォールバックを読み、復元は
行わない経路そのものです。BE-0393の単位2は、このスロットを保持するマップをメンバー向けに見積もって
おり（`MAX_SESSION_BINDINGS`、「1プロセスで同時に数千人のメンバー」）、その復元はGitまたはbundleの
取得で、セッションごとに一度支払うものです。ジョブごとに1つのセッションを発行すると、この取得を
ジョブごとに支払い、さらにメンバーのスロットを追い出してしまいます。

合成の`users`行を作らない理由も、ここで述べます。そのような行はロールの列も持ち、上と同じ
viewerデフォルトの分岐を再び開いてしまいます。しかも、その機械は`/api/orgs`が開示する名簿に載って
しまいます。

同じ理由で、監査の記録はリポジトリを*行為者*としては受け取りません。`actor_id`は`users.id`への、
nullを許すforeign keyです（`bajutsu/serve/server/models/audit_log.py`）。この制約を合成の行で満たそう
とすれば、費用は先ほどと同じです。`jobs.py`が行為者にuserの行があるかを確認してから書く`created_by`
とは違い、`_record_audit`は行為者をそのまま`actor_id`へ渡します。そこで単位3は、この接続点を変更し、
機械の主体については、`users`に裏づけのないログイン名ではなくnullを書くようにします。エントリ自体は
残します。`_record_audit`は行為者が偽値なら早期に返すため（`bajutsu/serve/authz.py:408`）、単にNoneを
渡すだけでは、列がnullになるのではなく行そのものが記録されません。リポジトリは、
監査エントリ自身のdetailペイロードに記録します。こうして、「どのパイプラインがこのrun
を始めたのか」を、偽のユーザー行なしに答えられます。

### 単位4 — テストとドキュメント

交換エンドポイントの検証は、JWKSとローカルで署名したトークンを注入することで、ネットワークもSimulator
も使わずにカバーします。

- 設定された鍵で署名され、設定された`aud`を持ち、列挙されたリポジトリから来たトークンは、そのリポジ
  トリのorgとして振る舞う機械セッションに交換されます。
- `aud`がそれ以外のトークンは交換の場で拒否されます。列挙されたリポジトリについて他の点では正当な
  トークンも同様です。
- 列挙されていないリポジトリのトークンは403で拒否されます。`repository`が列挙された項目と前方一致する
  だけのトークンも拒否されます。
- 2つのorgに列挙されたリポジトリは、リクエストが名指したorgへ交換されます。1つの共有パイプライン用
  リポジトリが、両方のorgで使えます。
- トークンのリポジトリを`allowedRepositories`に列挙していないorgを名指したリクエストは拒否されます。
  orgの名指しは選ぶだけで、権限を与えるものではありません。
- orgを名指さない交換のリクエストは、推測せずに拒否されます。
- immutableなsubject形式のトークンは`repository`クレームで認可されます。2つの`sub`の形は同じように
  振る舞います。
- 期限切れのトークン、更新してもJWKSに`kid`がないままのトークン、署名が壊れたトークン、そしてJWKSに
  到達できずキャッシュも失効しているものは、古い鍵セットを信頼せず、それぞれ拒否されます。
- ヘッダーが`none`を名指すトークンと、RSAの公開鍵バイト列で署名したHS256のトークンは、どちらも拒否
  されます。アルゴリズムは設定から決まり、トークンからは決まりません。
- 同じトークンを2回交換すると、1回目は受け入れられます。使い捨てはレプリカをまたいで成り立ち、1回目の
  レプリカがすでに使い切った`jti`は、2回目のレプリカでも拒否されます。同じレプリカへの再提示だけでは
  ありません。serve側で定めた最大経過時間を超えたトークンは、自身の`exp`がまだ未来であっても拒否
  します。`jti`を持たないトークンは、キャッシュを素通りさせずそのまま拒否されます。`iat`を持たない
  トークンも、経過時間の起点を持てないため、そのまま拒否されます。
- 想定利用者を設定していないデプロイは、他の点では正当なOIDCトークンを交換の場で拒否します。トークン
  が運ぶ想定利用者をそのまま受け入れることはありません。セッションごとの有効期限を保証できないセッ
  ションストア（`InMemorySessionStore`を含む）でも同様に拒否します。発行された機械セッションの
  有効期間は、提示されたトークン自身の`exp`を超えません。
- `import bajutsu.serve`は`joserfc`を一切引き込みません。import guardの`FORBIDDEN`集合が挙げる、
  他のserver専用の依存を引き込まないのと同じです。
- 機械セッションは許可リスト上のすべてのエンドポイントへ到達します。`POST /api/config`・
  `POST /api/compose`・`GET /api/config/content`・オペレーターのシークレットのエンドポイントでは
  拒否されます。データベースが配線されているかどうかで、この振る舞いは変わりません。
  `POST /api/compose`が拒否されても、orgのアクティブなバインディングと記憶された設定はそのまま残り、
  メンバーの次のセッションがパイプラインから何かを引き継ぐことはありません。
  `POST /api/oidc/exchange`自体は、事前のセッションもトークンも必要とせず、検証可能なOIDCトークン
  だけで到達できます。
- 両方のバックエンド（`handler.py`と`server/app.py`）は、どちらも`gate.py`を経由するため、
  機械セッションを同じように扱います。
- 境界の対象は`environment`、`ref`、`job_workflow_ref`です。これらのいずれかを設定したデプロイは、
  対応するクレームが異なる実行から来た、他の点では正当なトークンを拒否します。`environment`について
  は、クレームがないトークンも同様に拒否します。
- `environment`の境界を持つリポジトリと、境界を持たないリポジトリを並べて列挙したorgは、その
  どちらも交換できます。境界が効くのはその項目だけであり、org全体には及びません。
- 機械のアップロード（`bind_artifact`）と存在確認（`artifact_exists`）は、`default`ではなく、その
  リポジトリが列挙されたorgを解決します。マルチorgのデプロイでも、機械がdispatchしたrunでも、runの
  読み取りでも同様です。
- orgを廃止すると、`list_org_user_ids`が返すメンバーのセッションだけでなく、そのorgの発行済み機械
  セッションも取り消されます。
- 機械がdispatchしたrunの監査記録には、detailペイロードにリポジトリ名が残り、`actor_id`には`users`
  に裏づけのないログイン名ではなくnullが書かれます。`bind_artifact`も監査を残すため、runだけでなく
  アーティファクトのアップロードでも同様です。

`docs/self-hosting.md`とその日本語ミラーに、次を扱う節を追加します。

- ワークフローの権限と2つの環境変数
- オペレーターが設定すべき`aud`。省略するとOIDCの呼び出し形態そのものを無効にすることも含みます
- 交換エンドポイントと、それが発行する機械セッション。セッションのTTL（有効期間）が提示された
  トークン自身の`exp`を超えないことも含みます
- `allowedRepositories`の形と、交換のリクエストが照合先のorgを名指すこと。設定が効力を持つのは交換の
  ときだけであるため、リポジトリがリネーム・譲渡・削除されたとき、または絞り込みを強化したときに、
  項目を更新し、そのために発行された機械セッションを取り消す運用者の責務も含みます
- 任意の`environment`/`ref`/`job_workflow_ref`による絞り込み。`environment`の境界はクレームがない
  場合も、異なる場合と同様に拒否します
- `pull_request_target`とfork由来のpull requestへの書き込みトークンの危険
- パイプラインの後続の呼び出しは、すべてOIDCトークン自体ではなく発行されたセッションを提示すること

動作するワークフローの断片もそこに置きます。GitHub側の設定は2行であり、残りはserve側の設定だから
です。

## 検討した代替案

| 代替案 | 採用しなかった理由 |
|---|---|
| 毎回のリクエストでOIDCトークンを検証する方式（一度だけ交換する代わりに） | 対象のパイプラインは複数のエンドポイントを順に呼ぶため、使い捨ての`jti`では2回目以降の呼び出しをすべて拒否してしまいます。使い捨てをやめて再送を許せば、歯止めは経過時間の上限だけになります。リクエストごとの検証では、JWKSの取得とJWTの解析も、認証前に1つではなくすべての経路で到達可能なままになり、serveが発行していない資格情報を取り消すこともできません。 |
| 設定パネルからorgごとに長期のCIトークンを発行する | より単純ですが、本項目が避けようとしている秘密を再導入します。すべてのパイプラインに保存し、手で回転させ、ログから漏れ得るトークンです。しかも、どのリポジトリによる操作なのかを言えません。要点は保存場所ではなく身元の欠落です。 |
| BE-0313が絞った共有トークンをCIに再利用する | 意図的な決定を巻き戻します。共有トークンは身元を持たず全権であるため、worker以外のエンドポイントに戻すと、configを差し替えシークレットを読む能力をすべてのパイプラインへ渡すことになります。 |
| CIの身元にadminロールを与える | CIが必要とする5つのエンドポイントのうち4つが今日adminなので、序列としては合っているように見えます。しかし、それはconfigの差し替え、`GET /api/config/content`、オペレーターのシークレットのエンドポイントを一緒に連れてきます。どれもパイプラインには不要で、しかもすべて手に入ってしまいます。 |
| `sub`クレームで認可する | subjectの形式は、新しいリポジトリについてはすでにimmutableなIDへ変わっており、しかもリポジトリ単位でカスタマイズできるため、その形はserveが前提にしてよいものではありません。前方一致の判定は、列挙した名前を単に延長したリポジトリも通します。個別のクレームなら、どちらの問題もなく同じことを言えます。 |
| `repository`の代わりに、immutableな数値クレーム（`repository_id`/`repository_owner_id`）で認可する | これらのクレームはimmutableで、subjectのカスタマイズの影響も受けないため、名前の再利用という露出を根本から閉じられます。代わりに、リポジトリ名だけでは読み書きできない設定になります。項目を追加するには参照が要り、監査でもその項目がどのリポジトリを指すのか手がかりがありません。名前による形は、この読みやすさのために残しました。上で述べた運用者の責務は、その代償です。 |
| OIDCではなくGitHub Appのインストールトークンを使う | BajutsuはプライベートリポジトリのconfigソースのためにApp JWTへの署名をすでに行っており（BE-0224）、仕組みには馴染みがあります。しかしAppの登録と、デプロイへの秘密鍵の配布が必要です。得られるトークンが認証するのはパイプラインではなくAppであり、粒度の粗い身元を持つ共有の秘密に戻ります。 |
| 最初から任意の発行者のOIDCを受け入れる | GitLab、Buildkite、CircleCIもOIDCトークンを発行するため、org単位で発行者を設定できれば一般化できます。ただしクレーム名が提供者ごとに異なり、汎用の対応づけは目の前の課題より大きな設計になります。まずGitHub Actionsに絞れば、発行者は設定可能なまま残り、対応づけの設計は先に延ばせます。 |
